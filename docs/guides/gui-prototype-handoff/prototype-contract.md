# 原型交付与 Agent 实施规范

交接给：产品瑞华及其原型实现 agent。更新：2026-10-24。

> **现行交付路径提示（2026-10-28）**
>
> 本文的“将原型 HTML 直接打入 GUI 安装包”方案已被**组件化 `gui/` + `hyprial gui` / `hyprial gui dev` 开发预览**取代。当前正式 UI 主线是仓库根 `gui/` 的共享 React + TypeScript + Vite 实现，不再直接打包 vendor 原型 HTML，也不保留长期并行的第二套页面。
>
> 仍然有效的约束：产品设计归瑞华统一；研发可以补齐阻塞研发/验收的 UI，但必须保留原件与 hash、标记“研发补齐，待产品规范设计”、按 DEV-UI 登记并交回产品统一（沿用 N1.1 的原则）；业务动作、字段和状态必须可追溯；demo 与 live 严格隔离；无真实能力时明确不可用，禁止模拟成功；凭证不得进入页面日志、存储或普通 payload；视觉、fixture、真实后端和原生/真机验收分别记录。
>
> 新实施请先读 [GUI 设计与研发规范](../../../gui/docs/ui-development-standard.zh-CN.md)、[组件目录](../../../gui/docs/component-catalog.zh-CN.md) 和 [UI 变更交接模板](../../../gui/docs/ui-change-handoff-template.zh-CN.md)。下文 N1–N8 保留为旧原型直包交付的历史约定；与组件化主线冲突的打包、hooks 和资源路径步骤不再作为当前指令，其余产品协作与真实性规则继续适用。

目标：瑞华维护的一份原型进入 GUI 安装包，我们通过稳定桥接接入真实功能，不再重画页面或靠猜按钮文字接线。

本规范与《01-MVP-必要流程与页面补齐》配套。前者定义必须补什么，本篇定义如何交付才能稳定接入。它是新版交付约定；下面的接口形态是约定要求，不代表当前 v15 已具备、或某个新 API 已上线。

## 产品负责人先看这五条

1. **产品设计由瑞华统一，研发可先补阻塞 UI。** 页面缺失阻碍实现或测试时，研发可先做可用补丁并标注、登记，后续交瑞华规范设计；网络、模型、凭证和真实聊天由接入方实现。
2. **交互有稳定名字。** 按钮改文案或换位置，不应导致我们重写接入；删除或改变动作含义要列入变更清单。
3. **演示和真实运行彻底分开。** 演示可以有样例；真实运行无接口就显示不可用，不能退回假数据。
4. **交付可离线、可版本核对。** HTML 及依赖资源一起交付，版本、入口、资源路径与变化说明齐全。
5. **先自检再交付。** 新增功能同时提供状态样例与验收步骤；接入方再验证桥接和实际客户端，不用截图替代通讯验收。

## N1｜所有权与边界

瑞华：原型 HTML/CSS、页面布局、响应式、导航、交互和状态展示，以及稳定接入 hooks。

GUI 接入方：将动作映射到现有 CLI/类型化能力，投影真实数据，处理凭证存储、身份授权、平台差异、构建和原生验收。收到的原件按版本归档、校验 hash，不直接改原件修 UI；必要技术生成步骤独立且可审查。

原型不能直接调用 shell、读取宿主文件或保存 API Key，也不能自行把任意命令交给宿主执行。终端等高能力入口使用宿主明确提供的受控接口。

### N1.1｜研发先补，产品后续统一设计

GUI 研发线可直接补齐研发或验收必需、而原型缺失或阻塞的 UI，例如模型凭证表单、校验/启动按钮、聊天刷新、错误提示和必要交互。不必等待产品原型更新，也无需为每个此类补丁重新申请产品批准；仍按既有开发、测试、PR与合入流程执行。本条是上述所有权划分的明确例外，不授权假数据成功、凭证泄漏或绕过权限。

- **实现位置**：保留收到的 vendor 原件及 hash，在可审查的 UI 扩展、补丁或派生源码层实现。需要新增表单、文案或最小布局调整可以直接做；不以“原型不可改”阻塞研发，也不偷偷改归档原件。不得维护无法回合到产品原型的永久第二套页面。
- **明确标注**：相关源码/PR和交接记录标记“研发补齐，待产品规范设计”；内部测试界面在新增区域或统一说明入口显示简短标识，避免被误认为瑞华最终设计。不要在每个控件重复堆叠说明，也不要用标识遮挡正常操作。标识不是验收豁免。
- **逐项登记**：使用稳定编号（建议 DEV-UI-001 等），记录关联 M/N 需求、缺口与阻塞、平台/页面、实现路径、PR/精确 commit、使用的动作/字段、截图或复现步骤、验证范围、已知限制、待产品处理项与状态；截图必须脱敏。
- **集中交接**：在本目录的研发 UI 补齐台账中追加记录（实施首项时创建 `development-ui-register.md`，README加链接）。同一批迭代汇总给瑞华和其 agent，状态区分“研发已实现 / 已交接 / 产品已纳入 / 接入回归通过”。不能只留在聊天中。
- **收敛闭环**：瑞华后续统一视觉与交互，保留或明确迁移已有稳定 hooks。新版原型经差异核对和真实流程回归后，删除/替换已被覆盖的临时补丁与标识；产品尚未纳入前不先删掉可用入口。研发实现不等于产品确认，产品确认也不等于多端验收通过。

最小台账列：`编号 | 缺口/需求 | 平台/页面 | PR/commit/路径 | 验证与脱敏截图 | 待产品事项 | 状态`。本次只增加规则，不声称任何 UI 缺口已实现。

## N2｜稳定的动作与字段标识

- 用户动作使用稳定 `data-action` 或等价公开 dispatch 标识；实体使用稳定 ID，不能以列表下标、按钮文案或 CSS 顺序作为业务标识。
- 同一标识的含义与参数不静默改变。纯 UI 动作（展开/关闭/选页）和业务动作（保存/启动/发送）分开登记。
- 每个业务动作登记：用途、普通入参、敏感字段是否存在、需要的 capability、成功/失败状态、是否允许重复点击，以及关联需求编号 M1–M5。
- 敏感字段只声明字段名和用途，不在动作清单、事件记录或示例 payload 中填写真实值。Key 不经普通可记录的 dispatch payload，使用双方约定的专用通道。
- 旧版动作例如 `retry-model`、`retry-squire` 尽可能保留语义；新动作由双方映射确认。产品名称与按钮文案无需暴露内部动作名。

## N3｜宿主接入点与状态更新

新版应有明确的“宿主安装/初始化、动作提交、快照或增量更新、销毁订阅”接入点。具体函数名及 schema 由接入方与原型 agent 对齐后写入契约，不能各自创造同名但不同语义的 API。

宿主就绪并注入真实状态前，live 模式显示加载/连接提示。原型负责渲染；宿主负责身份、节点、模型、Squire、会话、消息的权威状态。UI 可以保存导航、草稿和展开状态，但不能自行把服务状态改为成功。

每个异步操作至少覆盖 idle/loading/success/error；必要时额外覆盖 unknown、unsupported、unauthorized。模型“已保存”与“已校验”、Squire“创建”与“在线”、消息“受理”与“回复”分别表达。消息按稳定 ID 去重，时间来自后端。

## N4｜demo 与 live 模式明确隔离

- demo：可使用固定 fixture，页面显著标“演示数据”；fixture 不包含真实凭证或个人隐私。
- live：禁用所有模拟请求成功、模拟回复、模拟在线节点和演示状态定时器。桥接缺失、契约版本不匹配、未知动作必须显示明确不可用，不能回退 demo。
- 由宿主显式选择模式。安装包生产入口不能让 URL 参数或普通页面点击切成 demo 后继续呈现为真实状态。
- 新版交付应提供显式模式入口，减少对内联脚本位置、函数文本或“恰好三个 style 块”等旧构建细节的依赖。

## N5｜能力、平台和秘密处理

宿主提供 capability；原型据此显示/隐藏/禁用入口并解释原因。不能仅按屏幕宽度判断这是移动端，也不能以按钮存在代表功能获授权。服务端仍独立检查权限。

桌面可配置本实例模型和 Squire；移动无本地 daemon/Squire，不能要求远端模型 Key；Web按当前宿主能力显示。窗口拖动、最大化、关闭等使用平台适配，不在 macOS/Linux盲用Windows按钮行为。

API Key 密码控件及生命周期按 M1。禁用秘密自动回填与持久化；日志、错误上报和截图不得包含秘密。真实消息、节点名称等外部文本进行转义或通过安全文本 API 渲染，不能直接拼入可执行 HTML。

## N6｜资源与布局

- HTML 可单文件，也可附本地 assets；入口及资源清单明确。禁止绝对开发机路径、file://资源、运行时 CDN/远程字体依赖或未声明的外链。
- 保留可自动外置的脚本/样式结构，兼容宿主 CSP；不以要求 `unsafe-eval` 或放开任意远程脚本解决接入问题。
- 窗口缩放、长文本、空列表、大列表均可操作。桌面检查普通/窄窗口与系统缩放；移动检查安全区、旋转、软键盘，输入框和发送按钮不能被遮挡。
- 交互元素支持键盘焦点，有可读标签；可点击图标应有辅助标签。错误信息不只靠颜色区分。

## N7｜每次交付的最小文件包

| 文件 | 内容 |
| --- | --- |
| 原型 HTML + 本地 assets | 完整离线资源；不要只交截图 |
| `DELIVERY.md` | 原型版本、入口、适用平台、契约版本、相对上版变化、已知缺口、验证步骤 |
| `actions.json` 或可读动作表 | 稳定动作/参数/能力/状态/敏感字段声明；未知项写待对齐，不虚构后端支持 |
| fixtures/或等价演示入口 | 无秘密的成功、空、加载、失败、权限不足、不支持状态 |

建议版本目录如 `fisher-v16/`，这是示例，不预定下一版编号。交付后由接入方生成文件 SHA256 与打包来源记录；不要手填无法复核的 hash。大型内部动作矩阵可以附带，但不是产品负责人阅读入口。

## N8｜原型 agent 的执行顺序与交付自检

1. 读取本文和 M1–M5；列出本次需求编号与涉及页面，保留不相关视觉设计。
2. 检查已有动作/状态契约；新增或破坏性变化列清单。接口不明确时提交一个具体问题，其他无依赖部分继续。
3. 实现入口、稳定 hooks、全部必要状态和 demo/live 分离；不代写不存在的宿主业务能力。
4. 用虚构 fixture 跑下面检查，保存步骤/结果；失败项如实记录。
5. 提交 N7 文件包。接入方做版本对比、动作完整性与桥接自动检查，再构建原生客户端。

| 必须检查 | 通过标准 |
| --- | --- |
| 全新用户模型配置 | 可输入、取消、保存、校验；失败不冒充可用 |
| Squire启动 | 有等待/失败/在线状态；重复点击不重复创建 |
| 聊天 | 新回复可更新，失败保留草稿，未知结果不假报成功 |
| 空账号/无组织 | 无假节点；本地路径可用；远端缺项有解释 |
| live无宿主 | 明确提示，不出现演示成功或自动假回复 |
| 未支持动作 | 禁用/提示，不静默失败 |
| 资源/版本 | 离线资源可加载；动作变化有清单；原型版本可追踪 |
| 响应式与键盘 | 目标平台输入、发送、错误提示均可见可操作 |
| 秘密/外部文本 | 不持久化或记录Key；脚本样式消息只当文本 |

原型侧检查通过只表示可交接。真实 API Key 校验、实际 Agent 回复、节点互通、安装更新由 GUI 接入方测试并另行记录，不要求瑞华凭空承诺。

## 历史快照与当前契约

v15 的动作矩阵、hooks 清单是接入调查快照，不是永久产品限制。本文描述新版交付目标；具体函数名、schema 和能力支持仍须在对应实现 PR 中对齐确认，不把规划当作已经上线的 API。
