### 2.3 How the daemon-request Contract Mock path works today

- Launch: `HYPRIAL_GUI_BACKEND_DRIVER=contract-mock` (+ optional `HYPRIAL_GUI_CONTRACT_MOCK_SCENARIO`, default
  `success`) with `hyprial gui`. `shell/impl/gui/backend/admission.py` admits the driver and the synthetic
  principal, `backend/source.py` starts `python -m contract_mock` (`contract/daemon-request/contract_mock/`) and
  captures its bearer from stderr, `backend/lifecycle/session.py` supervises it, then `gui/scripts/serve.mjs`
  starts Vite with `HYPRIAL_GUI_BACKEND_DRIVER`, `HYPRIAL_BACKEND_ENDPOINT`, `HYPRIAL_GUI_UPSTREAM_TOKEN`,

  `daemonRequestPlugin`. For the mock driver the host probes `/healthz` and `/mock/contract` and publishes every
  mock method as callable (`upstream.ts` `probeMock`).
- Session: the launcher hands the browser `http://127.0.0.1:<port>/#grant=<one-time grant>` (private
  `launch.url` hand-off for `--no-open`). `connectBrowserBackend()` removes the fragment, `POST /daemon/session`
  `{grant}`, receives view/generation/csrf plus the catalog, keeps the view proof in `sessionStorage`, and builds
  the one `HttpTransport`. One grant = one view; a second tab needs its own grant.
- Existing users of this path: `tests/daemon-request-host/contract-mock-loopback.test.ts` (vitest, real Python
  mock + host middleware), `tests/daemon-request-host/browser-acceptance.mjs` (`test:daemon-request-browser`,
  real CLI), `tests/support/isolated-daemon-host.mjs` (`installProductionBackendEnvironment`, daemon driver).

Trial (prototype `1e-3-helper-prototype.mjs`): one Python mock (`--scenario success --token <random>`), one
`startGuiServer({ mode: 'production' })` per view with the six environment variables set around the call, page
opened at `<origin>/#grant=<grant>`. Result: `200 POST /daemon/session`, then `org.list`, `org.network`, `hosts`,

### 2.4 Does Contract Mock cover what the reference scenarios cover?

Yes for data, with two structural gaps. `contract/daemon-request/openapi.json` declares 138 methods, 102
HTTP-exposed; **all 102 have examples** (420 cases): `success` for 101, `error` for 90, `empty` for 43,

1. **A whole-app scenario other than `success` is not usable**: under `--scenario empty` 59 methods answer

3. The old proxy served four scenarios from one GUI origin; the daemon-request host has one upstream, so one

## 3. Contract Mock today, and the single-source design

### 3.1 (a) Where the data and logic live

```
src/hyprial/daemon/impl/request_catalog/**/examples*.py     hand-written cases per method (REQUEST_EXAMPLES and
        │  uv run python scripts/verify/dump_daemon_openapi.py --write      the per-domain example tuples)
        ▼
contract/daemon-request/openapi.json      x-hyprial-methods[].x-hyprial-examples / x-hyprial-example-gaps
contract/daemon-request/http-envelope.schema.json            envelope shape + x-hyprial-status-by-code
        ▼
contract/daemon-request/contract_mock/   contract.py (load, re-validate, select)  service.py (handle)
                                         envelope.py  server.py (HTTP framing)    sensitive.py
```

`MockService.handle(method, params, authorization)` is a **pure, stateless** function of
(scenario, per-method overrides, method, params). Its logic, all of which an in-browser driver has to mirror:

1. bearer check (not applicable in the browser);
2. unknown method → 404 `METHOD_NOT_FOUND`; non-object params → 400 `INVALID_ARGUMENT`;
3. `agent.provider.login` accepts only the documented synthetic sentinel;
4. JSON-Schema validation of params (Draft 2020-12, `jsonschema`) → 400 `INVALID_ARGUMENT`, `not-dispatched`,
   message naming the first failing path;
5. case selection (`MethodContract.matching_case`, 25 lines): first case of the scenario whose declared params
   agree with the request; else first case whose disagreements are only on non-selector fields (a selector is a
   param name that also appears as a property name in the result schema, minus `idempotencyKey`/`operationKey`);
6. no case → 409 `MOCK_SCENARIO_MISSING` (with the recorded gap reason) or `MOCK_EXAMPLE_MISSING`;
7. envelope construction and status by code.

There is no state, no clock and no randomness except `requestId`. Steps 2, 3, 5, 6, 7 are small and
deterministic. Step 4 is the only one that cannot be mirrored without shipping a JSON-Schema validator.

### 3.2 (b) What the generated pipeline already does

- `gui/scripts/generate-reference-client.mjs` reads `contract/daemon-request/openapi.json` and writes
  `gui/src/client/generated/**` **and** `gui/src/dev/mock/examples.generated.json` (the raw
  `x-hyprial-examples` of the 102 HTTP methods, 215 KB). `npm run client:reference:check` regenerates both in
  memory and fails on any difference; it runs in `gate-gui.yml` and in `npm run verify`. So a generated data file
  with a `--check` gate against the Contract Mock source of truth **already exists**.
- Consumers of that JSON today: `dev/mock/agent-provider.ts` (`syntheticProviderLoginFiles` only),
  `tests/support/reference-fixture.ts` (an in-process unit transport that re-implements case selection by hand),
  `tests/fixtures/agents/agent-mutations.ts`, `tests/modules/dev04/org-rework-browser.mjs`.
- `dev/mock/use-contract-runtime.ts` is unrelated to Contract Mock despite its name: it wires the in-memory chat
  `LivePort`.

Extension (PR 1e-2): keep one generator entry point and add a second generated file produced **by the Python
mock itself**, so no reply logic is re-implemented in the generator:

```
uv run python scripts/verify/dump_contract_mock_scenarios.py --write | --check
   → gui/src/dev/contract-mock/scenarios.generated.json
```

Content (prototype: 420 rows, 395 KB): contract digest and version; per method the selector names, every case
with `{name, kind, scenario, params, status, envelope}` exactly as `MockService` answers it (so status mapping,
envelope shape, sentinel and schema-validation outcomes for the declared `invalid-params` cases come from
Python), and the precomputed `MOCK_SCENARIO_MISSING` reply per scenario without a case. `--check` exits 1 on any
byte difference. `npm run client:reference:check` calls it after the Node generator (uv is already required by
the GUI test suite and is installed before this step in `gate-gui.yml`). `examples.generated.json` is then
redundant; its four consumers move to the new file and it is deleted in the same PR or listed as pending.

The prototype also showed why selection must stay code: replaying each case's own params returns a different
case in 27 of 420 rows (several cases share params; first match wins). The in-browser driver therefore implements
steps 2, 5, 6 (about 60 lines) and looks everything else up.

```ts
export type ContractMockScenario = 'success' | 'empty' | 'unconfigured' | 'error';
export interface ContractMockSelection {
  readonly scenario: ContractMockScenario;
  readonly methodScenarios?: Readonly<Record<string, ContractMockScenario>>;
  readonly cases?: Readonly<Record<string, string>>;
}
export function createContractMockFetch(selection: ContractMockSelection): typeof fetch;
export function connectContractMock(selection: ContractMockSelection): Promise<BrowserBackendBootstrap>;
```

`createContractMockFetch` answers exactly the host contract: `POST /daemon/session`, `GET /daemon/request`,
`POST /daemon/request/<method>`, with the `X-Hyprial-Catalog-Digest` header. `connectContractMock` calls the
unchanged `connectBrowserBackend({ fetch, storage: <memory>, location: <synthetic grant>, history: <no-op> })`.
Everything above the wire — session parsing, `HttpTransport`, envelope validation, catalog pinning, generated
client, `createConnectedGuiCapabilities`, feature APIs, pages — is the product code, unmodified. No request leaves
the page, no path literal appears outside the driver, and `new HttpTransport` stays in `browser-session.ts`.

Proven by `1e-2-driver-prototype.test.ts` (2 tests green in the trial): a 45-line fetch built from the existing
generated JSON establishes a `contract-mock` session through `connectBrowserBackend`, `connection.client.agent.list({})`
returns the declared example, `createConnectedGuiCapabilities(connection)` builds, and the `error` scenario
surfaces as `DomainError`.

Documented non-goal: params that match no declared case and would fail schema validation get
`MOCK_EXAMPLE_MISSING` in the browser but `INVALID_ARGUMENT` from Python. The generated client's types keep such
requests out; the conformance table covers every declared `invalid-params` case by exact lookup.
