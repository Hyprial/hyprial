判据：空闲 daemon 的 CPU 基线  2026-10-23

状态：**判据交付，未实施、未测量**。本文不是「daemon 空转已确认」的声明。
来源：hq-adjutant 的一个反常读数 —— 空闲 CPU **1.70 → 1.86 核**，同期 IPC 延迟 17s → 7.5s
⇒ **延迟与 CPU 解耦**。解耦这条成立；而"空闲烧近两核"本身需要一条独立判据，本文就是它。

## 1. 为什么单独立一条

```
延迟与 CPU 解耦 ⇒ "慢"不能用"忙"解释 ⇒ 也不能用"不忙了"解释"好了"
⇒ 于是需要一个只看 CPU 的量：空闲时它在烧多少
⇒ 若空闲仍在烧,那么所有延迟测量都带一个共同原因,而它不是被测对象
```

⇒ 这条与 #1868（`HYPRIAL_IPC_ROUNDTRIP_SECONDS`）互补：旋钮让延迟**可测**，这条让"空闲时
本来该是多少"**可判**。

## 2. 判据（可直接实现为测试/巡检）

**采样时机（hq-adjutant 2026-10-23 更正；我原来写的"连续 3 个 60s 窗口"漏了这一格）**

```
⛔ 按 uptime 取点（"t+5min 测"是错的）
⛔ 用**代理量**判稳（线程数、内存、句柄都不行）
✅ 两级判稳（hq-adjutant 2026-10-23 合成：**漂移**与**振荡**是两种不稳，判据必须都抓）

```
局部稳（决定"能否开始采样"）
   相邻两窗 |Δ| ≤ 10% × w1

全局稳（决定"能不能报一个点"）
   ① 至少 3 个点，且跨 ≥ 10 分钟
   ② 无漂移：连续 3 点同向且累计 > 5% ⇒ 未稳
   ③ 无大振荡：max − min ≤ 25% × median ⇒ 否则未稳
⇒ ①②③ 任一不满足 ⇒ ⛔ 报单点，改报 `idle_range=[min, max]`
```

⇒ 为什么要两条：**只测漂移抓不到振荡，只测极差抓不到漂移**

```
我的"3 窗同向累计">5%   抓漂移  ✗ 抓不到 1.85 → 3.68（+99% 的单次跳变，非单调累积）
极差 max−min ≤25%×med   抓振荡  ✗ 抓不到持续单调回落（每步 Δ 都小，极差却可以很大）
```

⇒ 30 分钟内两级都未达 ⇒ 报 `NOT-EVALUABLE{unsettled}`，⛔ 拿最后一次当稳态。

**⚠️ 延迟那一格的更正（hq-adjutant 2026-10-23，与本判据的 CPU 侧无关，但同属测量纪律）**

```
我先前写"读路径 12–19s 变慢" —— 这句话**错**:
  · 15s 是 CLI 的 IPC deadline
  · 实测 infra-ops 06:40:42 三连:rc=1 IPC_TIMEOUT 15.2s / rc=0 13.3s / rc=0 6.6s(同一分钟)
  · 我自己的 canary 06:40:21 也直接报 IPC_TIMEOUT
⇒ 所以那些 ≥15s 的读数**被 deadline 截断**,不是延迟测量 ⇒ 真实延迟未知(右删失)
⇒ 正确说法:**org IPC 出现 15s 级超时**,⛔ "读路径变慢"
⇒ 报告里凡 ≥15s 的读数必须标 `(censored-at-15s)`,⛔ 与 <15s 的样本一起算平均/p50
```

⇒ 这与 `capability_probe` 的右删失是同一个坑：**用一个上限去测分布，超过上限的观测只告诉你"超过了"。**
```

**为什么不能用线程数判稳**（hq-adjutant 2026-10-23 实测）：

```
本次线程 815 → 826（变化 1.3%），同期 CPU 4.4 → 1.8 核
⇒ 按"线程变化 ≤2% 即稳态"会在 CPU 仍 4 核时判"已稳定"
⇒ 代理量与目标量在这里**不同向**：线程数几乎不动，而 CPU 掉了 60%
```

⇒ 通则：**判稳的量必须就是被测的量**；换一个量判稳，等于把"什么时候可以开始测"交给一个与结论无关的读数。

**为什么还要排除趋势**（hq-adjutant 2026-10-23 的序列）：

```
1.70 → 4.24 → 2.83 → 2.00 → 1.85      （同一机制，跨 t+5 … t+46）
⇒ 每一步的相邻 Δ 都在 10% 以内（Δ 越小越"稳"）,而整体在**持续下降**
⇒ 只看相邻 Δ 会把"缓慢回落"判成"已稳态"
⇒ 补一条:连续 3 窗**同向**且累计 > 5% ⇒ 判未稳
```

⇒ 这是"判据本身可以被趋势骗"的实例：**稳定性 ≠ 相邻变化小**。
两代实测（同一机制、同一命令）
    新 daemon t+5min   ⇒ 4.24 / 4.55 核      ← 启动期，恰是最吵的时刻
    同一 daemon t+13min ⇒ 1.86 / 1.81 核      ← 稳态
⇒ 所以"空闲"的定义不是"刚起来"，是"不再变化"
⇒ 两个读数都要报：启动期峰值 + 稳态中位数，⛔ 只报一个
```

```
窗口    连续 3 个 60s 的「无 IPC 调用」窗口（无调用 = 该窗口内无请求到达，需记录如何判定）
取值    每窗口取 CPU 中位数，再取 3 个中位数的中位数
目标    < 0.2 核（相对 1 核 = 100% 单线程）
归一    同报 **actor 数**（`hyprial top --json` 的 actors 数），并给出每 actor 值
        ⇒ 否则"0.3 核带 200 个 actor"与"0.3 核带 5 个 actor"读起来一样,而它们不是一件事
正控    有调用时必须**明显上升**（例如跑 N 次 `org work show`，CPU 应越过 0.2 核）
        ⇒ 没有正控时,一个"根本没在测量自己 CPU"的实现也会给出 0.0 核并变绿
负控    空闲窗口内不得有请求；若窗口被打断（有调用进来），该窗口作废并记录原因
```

## 3. 报数形状（⛔ 只报一个数）

**先加一格：一个总数分不出两种病**（hq-adjutant 2026-10-23）

```
threads             进程线程数
top_thread_share    最热线程占该进程 CPU 的比例
per_thread_cores    进程 CPU / threads（每线程平均核数）
sys_user_ratio      sys 时间 / user 时间（⇒ 系统调用密集 vs 用户态计算）
                     ⚠️ 必须写明分母是**进程**还是**单线程**（本机两种都用到过,且不可比）
```

**比值的通则（hq-adjutant 2026-10-23）**

```
一个比值必须带三件:分子 · 分母 · 分母的口径(进程/线程/窗口) + 时刻
⛔ 跨口径比较:16:1(单线程) 与 4.88:1(进程) 放在一起 = 把口径差读成行为差
⇒ 换口径时,要么重测成同一口径,要么把两个值各自标注、⛔ 并列当作趋势
```

两代实测的**两种形态**，聚合值几乎一样：

```
旧  threads 890 · 最热线程 44% · 16:1  ⇒ 成本集中在**一条热循环**
新  threads 838 · 最热线程仅 10.8% · 后三条各 9.6%（计数相同）· 4.88:1
    ⇒ 成本**摊在很多线程**上（同值同计数 ⇒ 更像周期性轮询而非单点死循环）
⇒ 两者都可以报成"空闲 ≈1.8 核",而修法完全不同:一个去修那条循环,一个去压线程数或周期
```

⇒ 因此「跑久退化」可能**换形式回来**：不是单线程变热，而是 **线程数 × 每线程常数**。
⇒ 报数必须三条一起：`threads` / `per_thread_cores` / `top_thread_share`。
⛔ 只报 `idle_cpu_median_cores`。
⚠️ 上面那两组比例（`16:1` / `4.88:1`）的**分母要写明**，否则它是一个没有定义的比值。

```
idle_cpu_median_cores   = 0.xx
windows                 = 3 × 60s      （被打断窗口数另记）
actors                  = N
per_actor               = 0.xx/N
threads                 = N
per_thread_cores        = 0.xxx         （idle_cpu_median_cores / threads）
top_thread_share        = 0.xx %        （最热线程占该进程 CPU 的比例）
positive_control        = 有调用窗口 CPU 升至 0.yy 核（须显著高于 idle）
verdict                 = pass / fail / NOT-EVALUABLE{missing_cell: …}
```

## 3.5 两次完整读数（同一 daemon，settle 后）

**第三次（06:35Z）**

```
idle_cpu_median_cores   3.68        （前一次 06:26 是 1.85 ⇒ 单次跳变 +99%）
threads                 844
per_thread_cores        4.36 毫核
sys:user                4.65
show p50                10.6s
log                     仍 0 条
⇒ 观测区间 **idle_range = [1.85, 3.68]**（约 2 倍跨度）
⇒ 按两级判据：**全局不稳**（既非无漂移、也非无振荡）⇒ ⛔ 报单点
```

**第二次（t+46，06:26:51Z）**

```
idle_cpu_median_cores   1.85        （相邻两窗 Δ3.1%）
threads                 839
per_thread_cores        2.21 毫核   （0.00221）
show（同一时刻）          0/5 超时，p50 3.7s
log                     仍 0 条
⇒ 与 t+35 的 2.00 核相比仍在下降 ⇒ 见"排除趋势"那条:两次都"相邻 Δ 很小",
   但序列 1.70→4.24→2.83→2.00→1.85 是持续回落,⛔ 已回到旧基线
```

**第一次（t+35）**

```
idle_cpu_median_cores   2.00        （相邻两窗 Δ6.5% ⇒ 按 ≤10% 判稳）
threads                 837
per_thread_cores        2.00 / 837 ≈ 0.00239
top_thread_share        11.3%       （旧 daemon 44%）
sys:user                4.71        ⇒ 系统调用侧占主导
                                   ⚠️ 这一格的**分母是进程**,⛔ 单线程(见下)
show（同一时刻）         0/5 超时，p50 3.0s
log                     仍 0 条
```

**三条分开的结论，⛔ 合成一句**：

```
延迟    好了   （0/5 超时，p50 3.0s）
记账    没好   （log 仍 0 条 ⇒ 冻结条件 ④ 仍不成立）
结构    变了   （最热线程 44% → 11.3%，threads 837，成本摊在很多线程）
```

⇒ 这是"**好了一个不等于好了**"的实例：同一个 daemon、同一时刻，一条读数正常而另一条仍坏。
报数时若只报"延迟已恢复"，读者会以为整件事恢复了。

**同口径复测（hq-adjutant 2026-10-23 06:23Z，全部进程级）**

```
threads               842
进程 sys/user         93.5 / 20.8  ⇒ **4.51 : 1**
最热线程              share 11.8%，sys/user **1.8 : 1**（**user 偏多**，与进程整体相反）
次热三条              6.8 / 6.7 / 6.9 : 1（**同形**，均 sys 偏多）
```

⇒ 读法（改成同口径后与我先前那句不同）：
```
· 次热三条同形且 sys 偏多 ⇒ 更像**一批同形线程在做 syscall 活**（轮询/锁/IO），⛔ 单点死循环
· 最热那条只 11.8% 且 **user 偏多** ⇒ 它是另一种活（用户态计算），⛔ 与那三条同族
⇒ 我先前写"更像周期性轮询"方向对,但把最热那条也算进去了 —— 同口径数据不支持那一半
```

**⚠️ 旧 `16:1` 与新 `4.88:1` 不可比（这条是"分母要写明"点出来的）**

```
旧 16:1   分母 = **那一条线程**
新 4.88:1 分母 = **进程**
⇒ 两个比值不是同一件事的两次数值,是两个不同对象的各自数值
⇒ 用它们做"代际对比"会把口径差读成行为差
```

**`sys:user` 这一格的读法（我加的，标为需复核）**

```
sys 侧占主导（4.71）⇒ 时间主要花在**系统调用**（轮询、锁、IO、timer），⛔ 用户态计算
⇒ 与 top_thread_share 只 11.3% 合起来看：更像"很多线程各自在轮询/等锁"，而不是一条死循环
⚠️ 这条是我的形状判断，⛔ 机制结论；机制结论要 perf/strace 一级的证据
```

## 4. 已知边界（写清楚，⛔ 假装没有）

- 本判据只回答「空闲时烧多少」，不回答「为什么烧」。
- **空闲读数（hq-adjutant 实测；只有 settle 后的读数可以互相比较）**
  ```
  旧一代 daemon（settle 后）        1.70 – 1.86 核
  新一代 daemon（settle 后）        1.81 – 1.86 核
  新 daemon t+5min                 4.24 / 4.55 核    ← **启动噪声，⛔ 参与代际比较**
  ```
  ⇒ 这两条结论有**排除力**（hq-adjutant 2026-10-23 指出）：
    若某个修复只改变**某一代**的行为（代际差量），它**不能**解释稳态空闲 CPU ——
    因为两代稳态都在同一区间。⇒ 排查顺序上应先排除"代际差量类修复"。
  ⇒ 结论只有两条，⛔ 第三条：
  ```
  ① 「跑久」没有让空闲 CPU 变高（两代 settle 后同一区间）
  ② 两代稳态都烧 ≈1.8 核 ⇒ 缺陷在**两代共有的路径**上，⛔ 在某一代的增量里
  ⛔ 不能说：t+5 的 4.24 核证明了什么 —— 那是启动期，与稳态不是同一个被测对象
  ```
- 这两个读数都来自抽样，**不是**本文的测量；本文只定义怎么测（窗口/中位数/归一/正负控）。
- actor 数会变（同一晚我见过 273 / 230 / 273）⇒ 分母必须连同 epoch 一起报。
- 若 daemon 有周期性任务（巡检、GC），"无调用"不等于"无工作" ⇒ 判据里要说明周期任务是否算作空闲。

**重启成本（hq-adjutant 2026-10-23 实测；讨论"要不要重启"必须带这一格）**

```
启动期成本 ≈ **17 – 35 核·分钟**
  依据:重启后 13 分钟窗口均值 3.1 核，稳态 1.8 核
        ⇒ 超出部分 (3.1 − 1.8) × 13 ≈ 17 核·分钟；按启动峰值 4.2 核算上界 ≈ 35
⇒ 「重启一下就好了」这句话的成本量级是**十几到几十核·分钟**,⛔ 一次瞬时动作
⇒ 任何"要不要重启"的讨论,若不写这一格,就是在拿一个未计价的动作当零成本
```

**读数冲突的处置顺序（hq-adjutant 2026-10-23，本机实测抖动是分钟级的）**

```
同一方法在不同时刻给出不同结论时：
  第一步  比**时刻**（谁的读数在什么时候取的）
          实例：他 05:55 p50 3.2s / 05:59 p50 9.6s / 我 2/2 超时（≈05:50-05:52）
          ⇒ 三组读数都真，只是被测对象在分钟级抖动
  第二步  比**口径**（同一条定义吗：窗口起止 / 分母 / 是否只看成功样本）
  ⛔ 第一步就跳到结论（"他测错了"或"我这边坏了"）
  ⇒ 本机 org.list 的抖动尺度是**分钟**，任何"你说 A、我说 B"的冲突先看时间戳
```
