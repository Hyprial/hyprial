# Ractor 性能验证计划：先验证完整路径，再迁移产品

状态：已有Dispatch内存功能的P0a标定完成，见 [结果与原始数据](../notes/ractor-dispatch-performance-2026-10-24.md)；本计划中的SQLite/ChangeFeed与完整daemon验证仍UNKNOWN。用户确认当前测量足以进入 [正式实施规划](actor-rustify-implementation-plan-2026-10-24.md)，不继续追加跑分。分层和减少自有actor机制是主要目标，不新增长期性能契约系统或另一条Python actor产品线。

## 1. 分两步验证

先行P0a已经直接调用现有DispatchStateAuthority，测得同批量接口下的native额外成本差异；它不含SQLite，不把该结果冒充以下两阶段已完成。后续仅随实际实现补齐必要验证。

**第一步：隔离的完整数据路径原型。** 实现 Python prepare → PyO3 → Ractor → 真实 SQLite事务 / scoped ChangeFeed → Python finalize，另测纯State/Snapshot/CAS。只做必要通用操作，不移植所有actor，不读取生产数据。性能计时包含所有转换、等待、实际提交和Python结果解释。

**第二步：隔离daemon中的一条实际调用路径。** 第一步显示收益后，再把一个有限资源接入候选构建，与相同业务算法的Python构建分别运行。此时才使用 `hyprial daemon status --json` 的ipcStats验证整机线程CPU、排队和超时，不能把独立crate指标伪装成daemon数据。每个运行实例只使用一种actor实现；对照不要求产品长期维护两个backend。

第一步通过只允许进入第二步，不代表完整迁移或生产验收。若第一步无稳定收益，先根据CPU分解定位边界开销，不通过扩大重写范围来寻找漂亮数字。

## 2. 公平基线

| 组 | 用途 | 要求 |
|---|---|---|
| A：修复算法后的现有Python路径 | 表示实际产品起点 | 必须含0.5.5/#1889及相关已完成算法修复；固定源SHA，不能用已知有自激/全量重复工作的旧版本衬托Rust |
| B：隔离Python粗粒度参考实现 | 分离接口批量化与换语言的收益 | 使用现有Python/Pykka能力实现同样的Snapshot/CAS/事务操作，不另建Python池化runtime产品 |
| C：Ractor/PyO3候选 | 判断native执行部分的额外收益 | 与B使用相同操作计划、算法、数据和持久化语义，Rust内部Python业务callback为0 |

B与C是主要性能对照，A给出实际产品变化的上下文；不得把A→C的全部收益归因为Ractor或Rust。当前可追溯的Inbox算法修复证据为#1891 head `630c54fd0`，报告中的产品候选源为`fecc25c85`；测量开始时重新固定所用源SHA和逻辑数据集，不把WIP称为已合并dev。

SQLite两侧必须对齐并记录版本/source_id、schema、journal_mode、synchronous、busy_timeout、事务边界与checkpoint设置。基线使用落盘数据库时，候选也使用同样落盘方式；不以关闭fsync、扩大批次或只更新内存换取“加速”。无法对齐时列出差异，不能作单因素归因。

## 3. 首轮负载

以下是实验参数，不是生产性能结论。避免展开所有参数的笛卡尔积；先覆盖这些代表场景，再根据瓶颈有针对性扩展。

| 场景 | 固定输入 | 核查目的 |
|---|---|---|
| 空闲等待 | 24个waiter、1000条初始记录、无新增消息 | version不变、唤醒/命令数有界、CPU接近空闲；不能仅因“每条命令更快”掩盖重复工作 |
| 无变化查询/条件写 | 并发1与24，批量1与32，固定请求轨迹 | 转换/排队成本、no-op路径、批量接口收益 |
| 混合读写 | 24个producer，1000条记录，固定90%读/10%实际变化轨迹 | 包含提交与通知的实际成本 |
| 写入与规模 | 8个producer，10000条记录，固定事务批次 | 数据量、SQLite和提交成本是否主导 |
| 单资源与多资源 | 同一轨迹分别集中一个资源、分散到16个独立资源 | 同资源串行是否保持，独立资源能否并行 |
| 容量边界/过载 | 同容量，逐级提高固定到达率 | 排队延迟、拒绝和超时；不得靠多拒绝请求获得低CPU |

第一步明确区分独立原型中的waiter和产品message wait；后者只能在第二步接入真实调用路径后宣称覆盖。

首轮预热15秒、计量60秒，每个选定场景做5组B/C配对，交替先后顺序并固定随机种子。采用相同到达轨迹与时长，分别记录提交/接纳/完成/拒绝数；队列等待从入队前开始计时。饱和吞吐单独测，不与固定负载结果混为一谈。若样本不足或有主机干扰，明确标记并在看结果前确定补测规则，不能只保留有利轮次。

第二步增加不少于25分钟的相同负载对照，覆盖原故障约20分钟后出现的时间尺度；此时仍只可声明隔离负载结果，不能宣称生产故障已复现。

## 4. 先正确，再计时

实现每项行为前建立会失败的测试，再修到通过并保留负对照。至少覆盖no-op不发布变化、真实提交推进版本、相关订阅唤醒、顺序/容量、等待超时不撤销操作，以及该原型实际声称支持的关闭和恢复边界。

逐条对照业务结果、提交事实、资源revision、最终逻辑数据摘要和应发生的变化通知。原始数据库文件hash可因物理布局不同而不同，不能代替逻辑一致性验证。改变决策或少做工作造成的速度提升不算通过。

第一步未实现的完整durable恢复不能标PASS；第二步前必须补齐所接入路径需要的语义。不得为跑性能跳过失败的正确性测试。

## 5. 需要的数据

- 端到端p50/p95/p99，队列等待、执行、提交到通知的延迟分解。
- 进程CPU与每个成功完成操作的CPU；Python prepare/finalize、转换、native执行的成本分解。线程CPU仅在测量机制可用且覆盖完整时报告，否则UNKNOWN。
- 到达/接纳/完成速率、拒绝、超时、错误、未结算操作和队列峰值。
- 线程数、RSS及随时间变化；macOS的峰值RSS等系统计量口径须写清，不能与其他平台单位混用。
- 第二步的ipcStats原始快照及分量threadCpuMs、Inbox排队与超时；统计窗口与负载窗口一致，记录诊断采样本身的开销。

数据留在新建的 `docs/notes/repro/` 实验目录：锁文件、构建/运行命令、源码SHA、参数、种子、逻辑数据摘要、逐轮JSON/日志、结果计算脚本。所有home/socket/db/cache隔离；不读取生产daemon或`~/.hyprial`。

## 6. 如何决定继续

正确性是前提。相同完成工作量下，关注CPU成本是否稳定下降、线程/内存是否改善、尾延迟与超时是否回退；给出全部配对结果和波动，不只给最好的倍数。额外吞吐若只来自更多CPU占用，必须明说。

收益若落在测量波动内、只存在于纯Rust计数器或被Python前后处理/SQLite吞没，就不宣称当前迁移值得。若需要自建大量actor机制才能获得收益，同样不符合此次选型目标。性能收益与维护成本均有依据后再进入产品迁移；任何未测项保留UNKNOWN/BLOCKED。
