# daemon request 迁移：交接文档

日期：2026-10-27。交接人：研发负责人（emergent-org-structure-refactor）。接手人：devusr。
集成分支：`intg/daemon-request`（从 `dev@3252c112c` 建立）。

## 1. 目标

Allen 2026-10-27 确认的目标：

> 后续 cli/gui 都只是对 daemon request 的封装……daemon request 只是一个 IPC 接口，接收参数返回 json。
> daemon request 改造后，src 内变为三个目录：hyprial，cli，gui，其中 cli 和 gui 到 hyprial 的唯一入口是 daemon request，
> daemon request 的改造就是机械化地将当前 cli 中的操作修改为 IPC 接口，再在 cli/ 和 gui/ 中重做渲染。

完成后的形态：

- `src/hyprial/`：daemon 与全部业务逻辑。对外只暴露 daemon request（IPC 方法：收参数，回 JSON）和 kernel 公开的 IPC 客户端。
- `src/cli/`：typer 命令，只负责参数解析、调用 daemon request、渲染结果。渲染允许按命令自定义。
- `src/gui/`：调用 OpenAPI。网关位置（hyprial gui 进程内或 daemon 内）在实现时与 Allen 商定，Allen 倾向放在进程内。

不在本线范围：daemon 内部实现方式（属于 actor-rustify）；GUI 页面本身（属于佳佳的 `intg/gui-refactor-freshestart` 线）。

## 2. 现状

- 其中多数命令经 `shell/impl/cli/commands/common/support.py` 的 `_daemon_request` 调 daemon；也有命令直接读写本地状态或 import 内部模块，没有经过 daemon。
- daemon 侧方法分发在 `src/hyprial/daemon/impl/ipc/router.py`，按方法名字符串分发；参数校验在 `ipc/params.py` 手写。方法清单需要第一步盘点。
- PR #1967（`feat/daemon-ipc-relocate` → `intg/daemon-ipc-client`）把 IPC 客户端从 CLI 私有代码搬到 kernel 公开面，e2e-verifier 三轮复核后 ACK，未合入。依赖关系图见同目录 `dep-map-daemon-ipc-client-2026-10-26.md`（cli-developer 编写）。
- 原计划的 PR-B（让旧 GUI 不再 import CLI 私有函数）取消：旧 GUI 整体删除，新 GUI 从零构建。

## 3. 推进步骤

1. **起点**：把 #1967 的改动改投 `intg/daemon-request`（rebase 到本分支），作为第一个 PR。生成的 CLI 和 GUI 网关都使用这个 kernel 公开客户端。
2. **设计文档，先交 Allen 审，审过再实现**。内容必须包括：
   - 全部 IPC 方法与 CLI 命令的逐项清单，每条标出：已走 daemon request / 需要新增 IPC 方法 / 属于引导命令白名单。
   - 引导命令白名单：不能依赖 daemon 运行的命令，例如 daemon start/stop、install、upgrade、doctor，以及要求 daemon 停止才能执行的离线操作（adapter downgrade-state、org repin）。只有白名单内的命令可以直接调用 `hyprial` 的公开函数。
   - IPC 方法的声明方式：参数 schema、结果 schema、错误码、是否流式。需要能导出 OpenAPI。
   - 交互式确认（如 org remove 的“预览 → 确认”）在 IPC 上的表达：确认必须绑定预览返回的 operationId。
3. **棘轮门禁，与第一个实现 PR 一起上线**：在 `scripts/ci/check_module_boundaries.py` 的同类机制上增加规则：CLI 命令代码不得 import `hyprial` 的 daemon/biz/identity 内部模块。现有违规登记为只减不增的名单。从此其他线新增或修改 CLI 命令只能走 daemon request。
4. **按命令组迁移**：一个命令组一个 PR，合入 `intg/daemon-request` 后尽快同步到 dev，不养长分支。迁移前在 OrgFS 工作项登记“正在迁移 xx 组”（`hyprial org work add --org group-internal`）。每个 PR 先红后绿，CLI 现有输出用测试钉住，确认迁移后逐字节不变（有意改动的除外，需在 PR 写明）。
5. **最后迁移的组**：org（tailcat 循环依赖修复正在改）、gui（佳佳的线）、transfer（cli-developer 的线），等这些线合入后再迁。
6. **目录搬迁放在最后**：全部命令都经 daemon request 后，用一个纯搬迁 PR 把 `src/cli/`、`src/gui/` 拆出来。提前在 hyprial-all-member 群公告冻结时间，合入后其他线统一 rebase。
7. **契约**：每个迁移的方法在 `contract/` 增加 schema 快照与语料；导出的 OpenAPI 进快照测试。改变已发布字段语义须按 AGENTS.md 写 Contract-Impact。

## 4. 与其他工作线的关系

- **actor-rustify**：改 daemon 内部（状态归谁、经哪个 mailbox 到达），不改 IPC 方法面。两条线只在 IPC 方法面接触；本线的 contract 快照就是 rustify 不能破坏的边界。可以并行。
- **GUI 重建（佳佳）**：其 `intg/gui-refactor-contract` 阶段直接使用本线导出的 OpenAPI，不另定义前后端约定。在此之前 `HYPRIAL_BACKEND_ENDPOINT` 返回 not implemented。
- **0.5.5.1**：本线不进 0.5.5.1。#1967 也不进 0.5.5.1（Allen 2026-10-27 同意）。目标版本 0.5.6。

## 5. 约束

- 遵守仓库 `AGENTS.md`：uv、结构门（每目录 7 文件、每文件 1000 行）、CLI 输出只经 `shell/impl/cli/output`、测试隔离、不碰生产 daemon 与凭据。
- 每个 PR 正文写动机、改动、验证命令与实测结果；未测项写 UNKNOWN/BLOCKED。
- 合入走 CI 基线比对：取 PR 的 push 运行失败 ID 与 `intg/daemon-request`/`dev` 基线的差集，仅 PR 出现的 ID 本地 head/base 各复跑 2 次，确定性只在 head 失败的才算回归。

## 7. 术语统一：host（Allen 2026-10-27）

Allen 原话：「好，请按照host修改文档并统一改写其他三个名字」。

现状（0.5.5.1 线 `contract/cli/surface.json` 计数）：同一概念有 4 种叫法：node 约 30 处（如 `org list`、`--node`、`agent top` 表头），machine 约 19 处（`--machine`、`--source-machine`、`--machine-key`），host 约 13 处（`hyprial host` 命令组、`agent host-invite`），device 约 6 处（org 命令与 OrgFS 设备记录）。

规则：

- 用户可见的 CLI 名词、参数名、帮助文字、输出字段与文档统一为 host；node、machine、device 一律改写为 host。
- host 只作名词，指“运行一个 hyprial daemon 的环境”。`agent host-invite` 等动词用法改名。
- 改名随本线迁移各命令组时一并完成，不单独发一轮改名 PR。已发布的 JSON 字段与参数名改名须按 AGENTS.md 同步 `contract/` 并写 Contract-Impact；旧参数名保留一个版本的弃用别名并提示新名。
- 代码内部标识符在迁移到的模块中顺带改名，不为改名单独动未迁移模块。
- 术语表 `GLOSSARY.md` 已登记 host 条目。
