# 生命周期接口对照：产品复核

状态：Draft，待下列业务决定确认。本文件复核 `design/lifecycle-flows@95d5a89a5` 的 8 份生命周期文档及 `gaps.md`；不改变原接口映射。技术现状以对照表标注的 `dev@4d676ec37` 为基线。`#2217`、`#2221`、`#2210` 在本次复核时仍未合并。

## 结论

67 个步骤的接口对照保留了原旅程，并把“已有 6、 有差异 46、仅 CLI 5、缺口 10”分开。6 个“已有”只存在于未合并的 PR，不能作为当前 GUI 可用能力。35 条“方法已存在但缺 MethodSpec”应由接口侧补声明；声明完成仍要分别核对权限、错误、状态和 GUI 接线。

产品侧需要修正证据与展示口径。一次请求返回成功，不能证明设备就绪、成员加入、模型可用、消息回复或飞书连接。对用户可见的完成条件保留；界面动作和客户端草稿不要求增加 daemon 方法。

## A 组：35 条缺 MethodSpec

**归属：接口侧。** 35 行都已有旧 IPC 方法，当前缺可供 GUI 消费的声明契约。研发按方法去重补 `MethodSpec`，写明可信身份、参数、结果、错误、权限、超时和结果未知时的核对方法。声明为 HTTP 可用与 GUI 实际接通仍须分别验证。

下列 A 组行还需同时处理产品语义；补契约本身不能关闭差异：

## C 组：5 条仅 CLI

**归属：可信宿主与接口侧。** 设备登录与准备不能由浏览器拼接 CLI 命令。飞书 App scope 授权及权限复核也须经过可信边界。研发宜定义固定宿主动作或 daemon 契约，并分别返回执行中、拒绝、过期、成功及未知结果。产品旅程中的“设备就绪”和“权限已授权”不因 CLI 能调用就降级为按钮点击成功。

对应行：`device.md / LC-DEVICE-01 / 1、2.a`；`message-connection.md / LC-MSGCONN-01 / 2.a、2.b、5.a`。

## 对 `gaps.md` 的处理建议

1. 保留 A 组 35 行、C 组 5 行和 D 组真正缺服务能力的行，按方法去重立项。A 组中的行为差异须独立验收。
2. 将复制链接、沟通方式本地选择、草稿保留从“daemon 缺口”改列为客户端任务或产品待决。修改统计前保留原 67/61 行基线，记录重分类原因。
3. 将 B 组的实时四步进度和 J10 错配标为设计修订；D1–D6 决定未确认前，不把对应接口建议写成已批准需求。
4. 产品侧修改对象文档后，研发重新映射受影响步骤；`gaps.md` 与对象表要保持同一版本。
